# Shared components index

**Consult this before building any UI element.** The rule (see `ui-patterns.md` → General principles):
*reuse is the default; a new one-off requires explicit justification.* Before writing a list, table,
panel, dialog, picker, inline editor, or button, find the shared component here (or grep for the
concept) and reach for it. If none fits, say why in your summary — don't quietly diverge.

This is a **living, seeded** index — it starts with the transaction/table/detail/primitive surfaces and
is meant to be extended as more shared controls are identified. It doesn't replace `ui-patterns.md`
(the *why* and interaction rules live there); it's the fast "what shared thing do I use for X?" lookup.
Paths are under `frontend/src/`.

**What earns a row:** a shared control — either *proven by reuse* (imported by **two or more** real
call sites) **or** *built to be shared* (deliberately designed as the reusable, canonical seam for its
job, even if only one caller exists today). A component built for reuse earns its row on day one; tag
it *sole use* (in the "Reach for" cell) until a second consumer appears, then drop the tag (re-survey
import counts when in doubt). What stays **out** is the incidental one-off — a component written for a single surface with no
reuse intent — until a second use makes commonizing worthwhile (verify by import count, discounting
same-name collisions). This is a "what's the shared way to do X?" lookup, **not** an inventory of every
component. A recurring shape that has no shared control *yet* belongs in the watchlist at the bottom,
not in these tables.

## Primitives, dialogs, interactions

| Reach for | Instead of building | Where |
| --- | --- | --- |
| **`ui.jsx` primitives** — `Card`, `Button`, `Select`, `Input`, `Badge`, `Spinner`, `EmptyState`, `Tooltip`, `PageHeader`, `Toggle`, `SelectAllCheckbox`, `CategoryMarker`, plus `getFormControlStyle` / `getFloatingPanelSurfaceStyle` | bespoke buttons/inputs/cards/badges/empty-states (note: a shared-`Button` audit is deferred — see `backlog/button-consolidation.md`) | `components/ui.jsx` |
| **`Button`'s `disabled` is simulated, not an attribute** — it dims, sets `cursor: not-allowed` and drops the handler, but never sets the DOM `disabled` property. So `button.disabled` is always `false`: a test asserting on it passes against *any* implementation and proves nothing. Assert the behavior instead — click it and check the call did not happen. (The buttons also stay focusable and announce as enabled to assistive tech, which the deferred audit above should take up) | `expect(btn.disabled).toBe(true)`, which is vacuous here | `components/ui.jsx` |
| **`AppDialog` wraps `actions` in `DialogActions` itself** — pass the buttons bare (a fragment is fine). Passing your own `DialogActions` renders two stacked footer bars with doubled borders and padding | `actions={<DialogActions>…</DialogActions>}` | `components/ui.jsx` |
| **`COMPACT_ACTION_BTN_STYLE`** (+ `variant="ghost"`) — the quiet, tighter footprint for a *repeated per-row* action that should read as a row control rather than the surface's verb (duplicate-detection rows, connection-card maintenance, the backup-key list's Export) | a full-size `Button` in a dense row, which shouts over the content beside it | `components/ui.jsx` |
| **`AppDialog` renders where it is mounted — it does not portal.** Fine for the usual case (a page-level component opens it), but a dialog opened from deep in a tree — a table row, a virtualized list — has its `position: fixed` overlay positioned and stacked against whatever ancestor established a containing block, not the viewport. The symptom is a dialog that surfaces *under* the page header with its title bar cut off, which is how the document viewer first shipped when the ledger row learned to open it. Wrap such a dialog in `createPortal(…, document.body)` (see `DocumentViewerDialog`), the same reason `RowPopoverPortal` exists in `TransactionRow.jsx` | opening `AppDialog` from a row/list cell and trusting `zIndex` to sort it out | `components/ui.jsx` |
| **`AppDialog` / `AppConfirmDialog` / `AppNoticeDialog` / `AppTextEntryDialog` (+ `DialogActions`)** — the standard dialog shells. The panel is capped at the viewport and **its body scrolls, not the page or the panel** — the header and the action buttons stay pinned, so a dialog with more rows than fit never puts its confirm button out of reach. A caller does not need to cap its own content height, and one that does should say why. **The `actions` slot is already wrapped in a `DialogActions`** — pass the buttons themselves (a `<>` fragment for more than one), never a second `DialogActions`, which renders its own divider shrunk to the width of the buttons and reads as a stray line above them | a hand-built modal; adding `maxHeight`/`overflow` to a dialog's content to make a long list usable | `components/ui.jsx` |
| **`FloatingPanel` / `OverlayBackdrop`** — floating surface + backdrop primitives | positioning a popover/overlay from scratch | `components/ui.jsx` |
| **`DropZone`** — the click-or-drop file target: hover/drag-over affordance, click **and keyboard** to browse, `onFiles(File[])`, `multiple`, `disabled`, and `children` as the label so each caller says what it wants dropped. | **`DocumentsPanel`** — attached receipts/invoices for one transaction: the list, the attach seam (drop, browse, **paste an image**, **paste text**, all one upload), the viewer, and the detach confirm. **`onDocumentsChange` must be a stable reference** — the panel reports its documents so a host can update the ledger's marker without refetching, and that report re-renders the host; an inline arrow there makes the panel refetch on every one of those renders, which loops. It reports the **list**, not a count: the row *opens* documents from the host's copy, so a count leaves a replaced document's id in place and the marker opens something that no longer exists. The paste target is a real `<textarea>` because nothing else receives a paste or offers right-click Paste (see `ui-patterns.md`) | a per-surface attach control; a paste handler on a `div`; passing `onDocumentsChange` inline; reconciling only a count | `components/DocumentsPanel.jsx` |

| **`VaultPassphraseDialog`** — the vault prompt every gated action raises (`set` / `unlock` / `change` / `request`). Pass **`onUnlockedByPasskey`** on any host that can settle a gate: without it the dialog offers the passphrase only, and a user with a passkey is made to type it | a surface-local unlock prompt, or wiring a passkey button to one screen and not the dialog | `components/VaultPassphraseDialog.jsx` |
| **`VaultSettingsDialog`** — managing the vault rather than opening it: unlock methods (change the passphrase, add/remove passkeys), **who can open the vault** with per-person **Remove access** (admin, never yourself), the access queue with **Approve**, and **Replace vault key** behind a confirm. Opens only while unlocked, which is the gate rather than the styling — approving and rotating both need the key in hand. It **fetches its own** members/requests/passkeys rather than reading a session prop: a surface that mutates a list has to own it, or its own writes never show up | adding a fourth control to the Connections `VaultStrip`, a page-local vault-management panel, or passing it `currentUser.vault_passkeys` | `components/VaultSettingsDialog.jsx` |
| **`vaultPasskey.js`** — the WebAuthn PRF ceremony (`registerPasskey`, `unlockWithPasskey`, `passkeyAvailability`, `PASSKEY_UNAVAILABLE`), plus **`runVaultPasskeyUnlock`** — the whole unlock in one call (params → ceremony → server) for every surface that opens the vault, and **`hasUsableVaultPasskey(user)`** for whether to offer it at all (a `pending` slot cannot open anything). Returns `{ ok, reason }` rather than throwing, because "this authenticator can't do it — use a passphrase" is an answer to give the user, not an error; only genuine faults propagate. Every reason has copy in `PASSKEY_UNAVAILABLE` and callers must surface **all** of them, cancellation included — a silently-abandoned ceremony leaves the surface looking untouched, which reads as "try again", not as "nothing happened" | calling `navigator.credentials` directly, treating a missing PRF as a failure, or swallowing a cancelled ceremony | `lib/vaultPasskey.js` |
| **`downloadUrl(url)`** — fetch a server-generated file and save it without navigating, so a non-200 raises the standard `buildResponseError` (with `detail.code`) instead of replacing the app with the raw response | `<a href={apiUrl}>` or `window.location.assign(apiUrl)` for a download — any error status then renders as a raw JSON page and no handler can run | `lib/api.js` |

## Recurring patterns without a shared control yet (watchlist)

Shapes that recur but haven't crossed the bar to commonize — either still too small to be worth a
control, or too divergent to unify without a leaky abstraction. They are **not** in the tables above
(nothing to reach for yet). The point of listing them: **when a new instance of one of these shows up,
surface it to the user** — one more copy may be the tipping point where extracting a shared control
becomes worthwhile. Deeper analysis + the audit process live in `backlog/refactor-audits.md`.
